# 네이티브 이식 첫 단계 — Explore 0.6.0-dev / DLL 0.4.0

## 방향 판단

현재 구조의 네이티브 전환은 기존 검증 경로를 재사용하므로 구현 위험이 더 낮다. 그러나 카메라
오프셋 코드를 C로 옮기는 것만으로 게임의 조준·상호작용 좌표가 바뀌지는 않는다. 원본 CT의
사격 좌표·상호작용 관련 제어 지점을 재현하는 쪽이 원본 동작에 접근하는 데 더 적합하다.
현재 실행 파일의 명령어 문맥·객체 소유권을 확인해야 하므로 완성 난도는 그쪽이 더 높다.
성공 확률을 수치로 제시할 근거는 없다. 공통 네이티브 기반을 먼저 만들고 확인된 원본 제어 지점을
그 위로 옮기는 순서다. 원본 CT가 현재 사용자 환경의 모든 문제를 해결한다는 실기 증거도 없다.

## 이번 변경

- REFramework의 Lua 생성 콜백으로 `re7_ots_native` API를 등록한다. 게임 빌드 검증 후 기존
  읽기 전용 상태 체인을 직접 샘플링한다. 새 Lua의 상태 전달 경로에서 파일 읽기를 제거했다.
- 네이티브 단조 시계를 카메라·모델·프롬프트의 시간 기준으로 공유한다. 상태·세대·재전송·
  포커스·350ms 만료·0.5초 준비 조건은 유지한다. 시계 오류는 해당 스크립트에서 차단한다.
- 파일 모니터는 구버전 Lua 호환용으로 남는다. 새 경로가 선택된 후 오류가 나더라도 파일로
  몰래 전환하지 않는다. 따라서 파일 I/O 전체가 제거된 것은 아니다.
- 정상 3인칭 프레임 사이에는 머리와 얼굴 재질을 그대로 표시한다. 내부 카메라 기준점 복원과
  실제 1인칭 복귀를 분리했다. 조준·인벤토리·상호작용·메뉴·오류·카메라 근접 시 숨김은 유지한다.
- `BeginRendering`에서 이번 프레임의 최종 카메라를 확인한다. 확인 실패 시 소유한 머리를 숨기고
  카메라를 복원한다. 잠긴 장면의 복원은 공식 API의 `no_dirty=true`를 쓴다. 렌더 콜백을
  등록하지 못하거나 직전 프레임에 관측하지 못하면 보수적인 기존 숨김 주기로 돌아간다.
- 모델 변경 전의 객체·소유권 검사와 쓰기 후 확인은 유지한다. 표시값이 같으면 쓰기만 생략한다.

## 오프라인 근거와 한계

`diagnostics/tools/probe_runtime_architecture.py`의 동일한 머리 2개·일반 노드 60개·
머리당 재질 5개 조건에서 **모델 경로만** 비교한 호출 수다. FPS나 전체 프레임 비용은 아니다.

| 모델 경로 / 프레임 | SDK 호출 | DrawSelf 쓰기 | 재질 쓰기 | 전체 검색 |
|---|---:|---:|---:|---:|
| 이전 3인칭 숨김/표시 반복 | 6,631 | 4 | 20 | 3 |
| 표시를 유지하는 3인칭 | 2,113 | 0 | 0 | 2 |
| 기존 1인칭 숨김 유지 | 398 | 0 | 0 | 0 |

실제 어댑터를 통과하는 100프레임 검사에서도 정상 3인칭의 반복 표시 쓰기 0회를 확인한다.
외부 재질 변경, 조준 복귀, 메뉴, 상태·시계 오류, 카메라 콜백 누락, 렌더 직전 위치 변경을 검사한다.
실제 Lua VM과 고정 버전 Lua 코어로 네이티브 등록을 실행하고, 파일 교체가 계속 실패해도
직접 샘플이 나오는지, 같은 tick에서 중복 seq가 생성되지 않는지 검사한다.

모델 SDK 조회는 아직 Lua에 남으며 정상 3인칭도 1인칭보다 검사량이 많다. 충돌 31개 레이어
검색, 동기 로그, 손 애니메이션, 실제 게임의 목표 선택과 사격 원점은 이번 단계에서 바꾸지 않았다.
사용자가 보고한 반복 전환·A버튼·중앙 시점·벽·손 문제가 해결됐다고 판정하지 않는다.
실제 Windows/Proton 로딩, REFramework 렌더 순서, FPS와 커스텀 Lua 내부 ABI는 미검증이다.

## 다음 이식 범위

1. 현재 빌드에 대응하는 원본 사격·상호작용 제어 지점의 명령어와 객체 문맥을 검증한다.
2. 검증된 제어 지점별로 비활성 상태의 네이티브 관찰 경로를 만든 뒤 수정 경로를 연결한다.
3. 충돌 레이어/부피 판정과 모델 조회를 네이티브로 옮긴다. 원인별 전환 기록으로 반복 복귀를 분리한다.

현재 워크스페이스에는 실제 게임 실행 환경과 해당 실행 파일의 명령어 확인 자료가 없어 원본 후크의
현재 빌드 매핑을 확정할 수 없다. 알려진 상수만으로 실행 코드 패치를 활성화하지 않는다.

## 검토 후 남은 경미한 사항

네이티브가 최초 검증 완료와 동시에 직접 상태를 읽으면, 시각을 먼저 읽고 검증 상태를 읽는
순서 때문에 한 번 `LIMIT`가 잘못 반환될 수 있다. 다음 상태 읽기에서 회복되며, 플레이 중
지속적인 차단으로 확인된 문제는 아니다. 독립 검토에서 경미한 후속 수정 사항으로 기록했다.
