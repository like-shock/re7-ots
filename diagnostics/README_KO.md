# RE7 OTS Diagnostics 0.1.0 — 스팀덱 설치 안내

**이 패키지는 3인칭 모드가 아니라 읽기 전용 진단기입니다.** 실행 파일을 외부에 올리지 않고, 스팀덱 안에서 원본 OTS CT의 검사 지점과 현재 게임을 대조합니다. 게임의 시점·밝기·조준·세이브를 변경하지 않습니다.

Windows x64 DLL 빌드와 자동 테스트는 완료했습니다. **실제 RE7·SteamOS·Proton·REFramework 안에서의 로딩과 동작은 아직 검증하지 않았습니다.** 새 네이티브 플러그인이므로 충돌 가능성이 0이라고 보장하지 않습니다. 첫 검사는 중요한 플레이 도중이 아니라 메인 메뉴에서 하세요.

## 1. 대상 환경

사용자가 확인한 RE7 기본 공개 버전(RT 계열), 기존에 정상 작동하는 REFramework, SteamOS의 기본 호환 도구 설정을 대상으로 합니다. 기존 dinput8.dll, Steam 시작 옵션, Proton 설정을 변경할 필요가 없습니다. RELit도 첫 검사에서는 그대로 두어 현재 환경을 기록하세요. 다른 모드가 만든 변경 흔적은 검출 대상이지만 어떤 모드가 원인인지는 자동 판정하지 않습니다.

Cheat Engine·Vortex·Fluffy·별도 런타임 설치는 필요하지 않습니다. 제공 DLL은 KERNEL32.dll/USER32.dll만 가져오며, REFramework 자체는 포함하지 않았습니다. 원본 .CT도 스팀덱에 복사할 필요가 없습니다.

## 2. 설치

게임을 완전히 종료하고 스팀덱 데스크톱 모드에서 압축을 풉니다. ZIP 안의 **reframework 폴더를 re7.exe가 있는 게임 폴더에 합쳐 넣으세요.** 기존 reframework 폴더를 삭제하거나 통째로 교체하지 마세요.

```text
RE7 설치 폴더/
├── re7.exe                            기존 파일, 수정하지 않음
├── dinput8.dll                        기존 REFramework, 교체하지 않음
└── reframework/
    ├── plugins/
    │   └── RE7_OTS_Diagnostics.dll     새 진단 플러그인
    └── autorun/
        ├── re7_ots_diagnostic_status.lua   새 상태 표시 스크립트
        └── 기존 모드의 Lua 파일들...
```

`reframework/reframework/plugins`처럼 폴더가 이중으로 들어가지 않도록 확인하세요. DLL은 autorun이 아니라 plugins에 넣습니다. Lua 파일은 상태 표시만 담당하므로 Lua만 설치하면 검사가 수행되지 않습니다.

공식 REFramework 로딩 규칙: DLL은 `reframework/plugins`, Lua는 `reframework/autorun`에서 로드합니다.
- https://refdocs.praydog.com/

## 3. 첫 진단

평소처럼 게임을 실행해 메인 메뉴에 도달합니다. DLL이 정상 로드되면 렌더링 콜백 60회 뒤 한 번 자동 진단을 시작합니다. 첫 진단에는 키 매핑이나 세이브 불러오기가 필요하지 않습니다.

기존 Insert/L4 버튼으로 REFramework 메뉴를 열고 다음 항목을 펼칩니다.

```text
Script Generated UI
  → RE7 OTS Diagnostics (read-only)
```

상태가 `STARTING → DISK_SCAN → MEMORY_SCAN → REPORTING → COMPLETE`로 바뀝니다. 빠른 단계는 화면에서 보이지 않고 넘어갈 수 있습니다. `COMPLETE`는 검사·로그 작성이 끝났다는 뜻이지, 모든 항목 통과나 3인칭 모드 호환 확정이라는 뜻이 아닙니다.

`Report:`에 표시되는 파일명을 확인한 뒤 게임을 정상 종료하세요. 상태 JSON은 저장되므로 다음 실행 초기에 이전 결과가 잠시 보일 수 있습니다. **파일명에 들어 있는 날짜·시간이 이번 실행인지 확인하세요.** 메뉴의 Refresh 버튼은 표시를 새로 읽을 뿐 재검사를 시작하지 않습니다.

상태 UI는 공식 `re.on_draw_ui()`와 `json.load_file()`를 사용합니다. 실제 게임 내 표시도 실기 검증 대상입니다.
- https://refdocs.praydog.com/api/re.html
- https://refdocs.praydog.com/api/json.html

## 4. 공유할 파일

```text
RE7 설치 폴더/reframework/data/RE7_OTS_Diagnostics/
  re7_ots_diagnostic_날짜_시간_밀리초_번호.txt
```

이번 실행에서 만든 `.txt` 파일 하나를 대화에 첨부하세요. 여러 파일이면 상태 메뉴에 표시된 파일 또는 가장 최근 파일을 선택합니다. 정상 완료된 로그의 **마지막 줄**은 다음과 같습니다.

```text
status=COMPLETE
```

처음에는 `status=RUNNING`이 기록되므로 마지막 줄을 보세요. `status=ERROR`도 분석에 필요한 결과입니다. 중간에 게임이 종료되면 마지막 완료 줄이 없을 수 있습니다. 로그를 해석하거나 특정 주소를 찾을 필요는 없습니다. `re7.exe`, 세이브, 게임 폴더 전체, 메모리 덤프를 공유할 필요가 없습니다. `status.json`은 화면 표시용이며 상세 결과가 아닙니다.

## 5. 재검사 (필요할 때만)

**키보드 F9**를 눌렀다 떼면, 검사 중이 아닐 때 새 보고서를 만듭니다. 스팀덱에서는 사용하지 않는 후면 버튼 하나를 키보드 F9에 대응시키면 됩니다. 기존 Insert/B 매핑은 바꿀 필요가 없습니다. 창이 게임에 포커스된 상태에서 입력하세요.

최초 한 번의 자동 검사만으로 현재 단계에 필요한 코드 비교를 시작할 수 있습니다. 세이브를 불러온 뒤 F9로 다시 기록하는 것은 후속 스냅샷용이며, 객체 수명·카메라 의미 검증을 대신하지 않습니다.

## 6. 진단 범위와 해석

| 내용 | 범위 |
|---|---|
| 원본 기준 | 사용자가 제공한 OTS RT 8.02 CT의 SHA-256 고정 |
| 코드 위치 | 주요 4개 블록 71개 + 별도 Fullbright 7개 = 78개 |
| 바이트 검사 | AOB 패턴 및 전체 수정 예정 구간(CT DISABLE 복원 바이트 기준) |
| 파일/실행 비교 | 로컬 re7.exe와 현재 로드된 주 실행 모듈을 별도로 검색 |
| 고정 RVA | 16개 위치의 이미지 범위·읽기·실행 페이지 여부 확인 |
| 자동으로 확정하지 않음 | 실제 객체 종류, 포인터 체인의 의미, 정확한 후크 설치 주체, 조준·벽 충돌·장면 전환 정상 동작 |

| 주요 결과 | 의미 |
|---|---|
| BYTE_MATCH_ONLY | 두 검색 범위에서 유일한 위치와 전체 예상 바이트가 일치. 플레이 가능 판정은 아님 |
| LIVE_BYTES_CHANGED_AT_DISK_CANDIDATE | 파일의 후보는 맞지만 같은 위치의 실행 중 바이트가 다름. 원인은 미확정 |
| FULL_PATCH_BYTES_MISMATCH | 짧은 패턴만으로는 부족하며 전체 구간이 CT 예상과 다름 |
| AMBIGUOUS_PATTERN | 패턴이 여러 곳에 일치해 자동 선택 불가 |
| PATTERN_NOT_FOUND_IN_SCANNED_SCOPES | 검사한 범위에서 찾지 못함. 암호화/로더 변환/읽기 실패/버전 차이 등 원인은 별도 조사 |
| BYTE_MATCH_ONLY_INCOMPLETE_SCAN | 후보 바이트는 맞지만 메모리/파일 검색 완전성을 확인하지 못함 |
| LIVE_BYTE_MATCH_DISK_UNAVAILABLE | 파일 접근은 실패했지만 읽을 수 있는 실행 메모리에서 후보가 발견됨 |

파일 검색은 PE에 매핑되는 섹션의 원본 데이터만 검사하고, 파일 오버레이·zero-fill·섹션 경계를 가로지르는 패턴은 제외합니다. 메모리 검색은 주 모듈 SizeOfImage 안의 읽기 가능한 committed 영역만 검사합니다. 두 검색 범위가 완전히 같지 않으며, 메모리 스냅샷은 원자적이지 않습니다. 일치 개수만으로 전체 호환성을 단정하지 않습니다. 전체 CT의 모든 부가 기능을 검사하는 것도 아닙니다.

고정 위치가 읽힌다는 것과 올바른 객체라는 것은 다릅니다. 첫 버전은 고정 슬롯의 값이 모두 0인지까지만 기록하며, 게임 객체 포인터 체인을 따라가거나 게임 함수를 실행하지 않습니다. 다른 모드의 소유자를 밝히는 검사도 수행하지 않습니다.

## 7. 안 되거나 되돌릴 때

**상태가 없거나 로그가 생성되지 않으면:** 폴더 이중 복사 여부, DLL/Lua 위치, 게임이 메인 메뉴까지 렌더링됐는지 확인하세요. 게임 폴더의 `re2_framework_log.txt`에서 `RE7_OTS_DIAG` 또는 `RE7_OTS_Diagnostics` 로딩 오류를 확인할 수 있습니다. 진단 폴더 권한 문제도 오류로 기록합니다. Lua 메뉴만 나타나는 것은 DLL 로딩 성공을 뜻하지 않습니다.

**게임이 충돌하면:** 다시 실행하기 전에 추가한 두 파일을 게임 폴더 밖으로 옮기세요. 기존 dinput8.dll과 RELit은 그대로 둡니다. 첫 버전의 실제 Steam Deck 동작은 미검증이며, 반복해서 충돌을 유도할 필요는 없습니다.

제거는 게임을 완전히 종료한 뒤 다음 두 파일만 옮기거나 삭제합니다.

```text
reframework/plugins/RE7_OTS_Diagnostics.dll
reframework/autorun/re7_ots_diagnostic_status.lua
```

로그 폴더는 남겨도 됩니다. 진단 DLL은 실행 중 코드가 해제되는 것을 막기 위해 프로세스 종료까지 로드 상태를 유지하므로, 실행 중 네이티브 플러그인 재로드로 제거하려 하지 말고 게임을 종료하세요. 게임 실행 파일·세이브를 패치하지 않았으므로 해당 파일의 복구 작업은 없습니다.

## 8. 기록·개인정보

네트워크 통신, 전체 메모리 덤프, Steam 계정·세이브 조회 기능은 없습니다. 로그에는 실행 파일의 SHA-256·PE 식별 정보, 원본 CT 해시, 모듈 상대 위치(RVA), 패치 구간의 제한된 바이트, 오류 상태가 포함됩니다. 절대 설치 경로·계정 이름·실행 중 객체의 절대 포인터 값은 자체 보고서에 기록하지 않습니다. 기존 REFramework 로그에는 설치 경로 등이 있을 수 있습니다.

영구적으로 작성하는 파일은 자체 진단 폴더의 보고서와 상태 JSON뿐입니다. 게임 코드·데이터를 변경하는 API를 사용하지 않지만, DLL 로딩 및 작업 스레드의 메모리 사용 자체까지 없는 것은 아닙니다. 진단 중에는 파일 읽기와 CPU 사용이 발생할 수 있습니다.
